## 一、认账与根因（如实）

CPU 满载说了四次（O-1738→O-1819→O-1136→今日追问）才见实况——根因两条：
1. **判定与处置分离**：水位探针（watermark）只「记录+点名」，无自动纠偏动作；audit 五旗（瞎跑/白跑/僵尸）只判不杀。发现≠纠正。
2. **发令不验证**：GM 发满载令后未在 30min 内回查执行水位——令落地≠令生效。

## 二、机制与规则（立法 · 长效）

### R1 水位闭环：从「记录」升「处置」
- watermark 每 10min 记录（已有）不变；**新增行动层**：py<70% 且存在可跑 CPU 批 且 连续 ≥3 次采样（30min）= **水位红牌**：
  - 僵尸进程（py 龄>45min 零 CPU 增量）→ **自动杀掉 + checkpoint 续跑重启**（本批已有 checkpoint 文化，杀=零损失）；
  - 可跑批被门/被队列卡 → **自动升级**：轮报告置顶 P0 + dashboard 水位红牌 + GM 呈报面（GM 豁免权即时行使，禁止闲置算力等门——O-1612 范式固化）；
  - 队列真空 → bandit 队列自动取下一批排队预注册（「队列永不清空」条款从纪律升机械动作）。

### R2 进程健康：出问题及时杀+重启
- audit 五旗从「判定」升「判定即处置」：瞎跑（高烧无产出 15min）=杀；僵尸=杀+续跑；单核占道大构建（预期多核实跑单核）=诊断记录+收割后强制多核化改造。
- 杀进程三查保险（防误杀）：查 checkpoint 在位（可续跑）、查非交互会话进程（GM/用户进程白名单豁免）、查杀后重启动作落日志。

### R3 轮序重排：水位红=下一轮第一优先
- 轮会话 S3 执行顺序固定化：**水位红牌 > 修红 > 其他一切**。每轮报告首行必含 watermark verdict（绿/红+原因一句话）。

### R4 发令验证纪律（GM 自身规则）
- GM 发任何资源/算力类令后，**必须 30min 内回查一次执行水位**（watermark/audit 实读），未生效即当轮处置；此后每 2h 抽查一次。本纪律适用于所有 GM 会话（记忆+章程固化）。
