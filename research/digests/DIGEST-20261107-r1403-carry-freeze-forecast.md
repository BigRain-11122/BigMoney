# DIGEST 2026-11-07 r1403 (bm-c) · 账本会不会冻：不是今天，而是现金腿补齐的那一天

**问**：`MSG-20261107-1637` 断言下一次 `etf_book_forward.py run`「极可能把整本账冻住（exit 3）」。
这是一句关于算术的话，可以量，不必怕——前提是**只重算不写账**。

**答**（`scripts/etf_book_carry_repro.py`，读 `LEDGER.json` + 现面板重算，零写入）：

| 面 | 读数 |
|---|---|
| 已结 bar（10-23 / 10-26 / 10-27） | 逐位复现，最大偏差 **0.000e+00** |
| 未结 bar（10-28 … 11-06，8 根） | 最大偏差 **9.956e-07**（1e-9 闸的 996 倍） |
| 今天跑 `run` 会不会 exit 3 | **不会**（闸只警已结 bar，3 根全过） |

**真正的答案是时间轴上的**：闸门只警**已结** bar，而这 8 根未结的原因正是「利率没到」。
现金腿一旦补齐，这 8 根就变成已结——同一批差额立刻进入闸。逐档预测（把 carry_last 依次
推过每一根）：

| 现金腿补齐到 | 会卡的 bar |
|---|---|
| ≤ 2026-10-29 | 0 根 |
| 2026-10-30 | 1 根（10-30，1.66e-07） |
| 2026-11-02 | 2 根（+11-02，6.63e-07） |
| 2026-11-03 | 3 根（+11-03，8.24e-07） |
| ≥ 2026-11-04 | **4 根**（10-30 / 11-02 / 11-03 / 11-04，最大 9.96e-07） |

所以对 bm-a 的动作含义很具体：**补数与改述必须在同一窗做完**。只补数 → 下一轮账本 exit 3；
而且这不是 `--rebase`（账没错），是 `restate_provisional` 那条已存在的披露路径
（发布值、结算值、差额、当时还在长的面板日，全部留痕）。

**读者带走三句**
1. 「会不会冻」有时间轴：今天的绿不等于下周的绿。判据要问「哪一天它会变红，为什么」。
2. 差额的正身只答了一半：4 根 bar（10-30 / 11-02 / 11-03 / 11-04）的 NAV 位移是 carry 差额的 **1.5–4.2 倍**，即同一批 bar 上还有一处**未归因**的重算差异。本面把它逐根点名，不并入 carry 解释、也不动阈值。
3. 重算面必须零写入：先读账、再重算、最后只用**活闸自己的** `partition_settled` 切分（E289 一条律一份实现），否则量出来的「会不会冻」是另一个 World 的答案。
