# E563 · 短回执是不是它自己那张表的前缀（r1590 bm-b · 2026-11-08）

E561 留下一句「一个停住的运行和一个 `--only` 运行在文件里完全相同」，E562 把「被杀」这一支排除掉了（三个跑器都在 leg 循环**之后**才一次性落盘），于是只剩「过滤」。但这句话只有在**回执从来不与表头对齐**时才成立。本轮直接量形状：

对 E561 已发布的 159 份短回执，取它自己那一轮（`join_commit`）的 `Tools/s6_chain_bm<X>.py` blob，读 `LEGS` 表的**顺序**，再把回执里每一条腿的名字映射成表内下标，按顺序判类。

## 读数

| 类 | 计数 |
|---|---|
| 精确前缀（= table[0..n-1]） | **4** |
| 前缀但中间跳了一条 | 10 |
| 表内有序子集、但起点不在第一条 | **138** |
| 同一批腿换了顺序 | 0 |
| 名字不在那一轮的表里 | 6（其中 4 个在**今天**的表里，8 个在任何现表里都没有） |
| 同一条腿出现两次 | 0 |
| 表不可读 / 回执不可读 | 0 / 1 |

159 份里 152 份（95.6%）完全按表序运行。**135 份单腿回执里，0 份跑的是表头第一条腿**——单腿运行全是「过滤到这里」，没有一份能读成「按顺序跑到第一条就停」。

## 结论

- **「过滤」是唯一能解释 138 份的机制**：没有任何有序停止会从第 4 条腿开始。
- 但**「停住」没有被彻底排除**：4 份精确前缀（2/4/4/4 条腿，全是表头）在文件里与「表在前 N 条腿处结束」或「按顺序跑到第 N 条被杀之后仍然写成文件」无法区分。所以 E561 那句话的正确收窄是：**绝大多数短回执是过滤，极少数（4/159）仍是形状相同的两义**。
- **6 份「名字不在表里」是一个额外发现**：其中 4 份的名字在今天的表里存在——说明那份回执是由**比它接合到的提交更新的 runner** 产出的；另 8 个名字在任何现表里都不存在（`item_store_between`、`pool_dualrun_reconcile` 等），即回执来自别的程序或被改名的腿。这动摇了「按轮号提交接合 runner」这个前提的 4/159。

## 可复用教训

1. **「看起来一样」要落到顺序上再判**——只看行数与表长，159 份全是「两义」；把名字映射成表内下标后，138 份立刻只有一个解释。分类的力度取决于证据的解析度，不是样本量。
2. **接合键正确不等于接合时点正确**——按轮号找提交能接上 runner，但那份 runner 可能**比产出回执的那份旧**（4 个名字只在今天的表里）。任何「用提交时的源码当证人」的研究都必须发布「证人比产物新/旧」这一列，否则会把新腿读成外来名。
3. **空集也要有自己的类**：`单腿 & 表头` 这一格是 0，但它是本轮最有力的一条读数——没有它，「过滤」和「停止」还会被读成对半开。零命中的格要单独发布，不要并进别的类。

## 边界

纯静态：不执行任何 runner、不重写任何回执。每行只携带腿名与表内下标（`leg_names` / `leg_indices`），所以闸能在不读任何 blob 的前提下重算类。今天的表只用于给外来名做「是否晚于接合提交」的注解，属漂移面、不进闸。
