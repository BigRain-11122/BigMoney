# 合约盘有了生产者：一个「没人写」的目录，和一个被追问了两轮的 ￥84,480

**轮次**：r1847（bm-c）｜**实物**：`scripts/update_futures_contracts.py`（selftest 8/8）、`results/futures_contracts_refresh.json`、`data/futures_contracts/*.csv`（8 个在交易合约，尾日 2026-11-16 → 2026-11-19）

## 问题是怎么被发现的

- **r1843**：`idx_fut_contract_roll` 发布 11-18 的读数，而它挑合约用的 `data/futures_contracts` 最后写入是 2026-11-16 22:30，`git ls-files` 计数 0，全仓没有任何脚本写它——不是慢车道，**是没有车道**。
- **r1845**：账本里 IC2612 / IM2612 的 2026-11-17 各一根 bar 在合约盘上找不到，而印出来的收盘 6194.8 / 6023.0 与主力连续当天一模一样，撑着 ￥84,480 的绝对盈亏。当时只能写「两种读法都成立，这张盘分不出来」。

## 本轮做了什么

给这个目录一个仓内生产者：用主力连续盘已在用的同一个 sina 日线端点（`scripts/update_futures.py::RAW_URL`），刷新**还在交易**的 8 个合约（`IC/IF/IH/IM` × 2611/2612），append-only + 逐行 overlap 校验，写盘原子（tmp+replace），2.5s 间隔，连接级 3 连败熔断。

实跑：**panel_max 2026-11-16 → 2026-11-19，追加 23 行，0 处 overlap 失配**。再跑一次：`ALREADY_CURRENT / appended 0`。

## 那个 ￥84,480 的答案

盘补齐之后重跑 `futures_book_marks`：

| | 补盘前（r1845） | 补盘后（本轮） |
|---|---|---|
| verdict | `BOOK_MARKS_UNSUPPORTED` | `BOOK_MARKS_SUPPORTED` |
| 无支撑 bar | 2 根 | **0 根** |
| 无支撑金额 | ￥84,480 | **￥0** |

源端 IC2612 的 2026-11-17 收盘 = **6194.800**，IM2612 = **6023.000**，与账本逐位相同。也就是说：**这两根 bar 是真的合约收盘，不是抄错了源；丢的是盘上的行**（面板自 11-16 22:30 起没人再写）。与主力连续相同并不奇怪——那两天 IC2612 / IM2612 就是当月合约。

这条结论只在补盘之后才立得住：23 行 overlap 校验零失配证明了「源与旧盘在重叠处逐位一致」，所以差异只可能来自缺行，而不是两套口径。

## 仍然没解决的（如实）

1. **8 个在交易合约之外的 410 个文件仍是冻结快照**。本轮只刷新「最近 5 个交易日还有 bar」的合约；已到期合约的尾巴是终态，不需要刷新，但这也意味着「某个合约尾巴是否被改写过」这件事仍然无人看守。
2. **这个生产者没有计划任务/车道宿主**。它是链腿上的一步（`Tools/s6_chain_bmc.py` 里排在 `futures_book_marks` 之前），链停它就停；r1843 提的「要么给生产者，要么标成冻结快照」现在算前半句，后半句（把「这是谁写的、多久写一次」印到读者那一页）仍未做。
3. **11-19 的 bar 是收盘后取的**，若 sina 之后回改当日结算价，本面会以「下一次运行时的值」为真，本次的值没有独立留档（overlap 只覆盖已落盘的行）。
4. **`idx_fut_contract_roll` 本轮随之重算**（cutoff 11-18，admitted IC/IF/IM），但它「用哪一天的盘挑合约」这句话还没有印在读者面上——那是下一轮的事。
